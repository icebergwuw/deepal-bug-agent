## 对 Bug/Jira 工作的影响

1. Jira 是需求和 bug 的正式流转平台，但结论必须能追溯到 Drive、PRD、UE、功能列表、语音平台或项目正式目录。
2. 产品创建 story 后，不是只建一个票结束；如果涉及 UI、语音、AIS、安卓等多方责任，要同步创建或推动对应 task/story。
3. 二级 story 如果需要多个研发部门协作，应拆到各方分别有 story，避免一个票跨多团队导致责任不清。
4. PRD/UE 定稿后应同步到 Project Committee 或项目正式目录，并把链接贴回 Jira。
5. Bug 转需求时，需求描述必须写清功能点链接、query/触发条件、当前行为、目标行为和责任方。
6. 语音相关需求需要结合语音系统填写规范、执行策略和 TTS 规范，不能只写自然语言描述。
7. 读取到平台账号、密码、访问口令等敏感信息时，不沉淀明文，不在回复或 bug 表中复述。

## Jira 规范学到的规则

1. Story 由专业负责人按职责创建：系统工程师负责系统级/灰色需求，产品负责人负责产品交互类需求，设计负责人负责 UI 需求。
2. Story 描述必须带产品文档链接，Epic Link 不能空，并准确指派给研发部门。
3. Task 是开发拆解实现步骤，产品经理和系统工程师不应该拆解 Task；产品侧要把 story 转给 TPM 或 Tech Lead，并推动他们拆 task。
4. Bug 是测试或研发自测发现的问题；如果是测试预期错误、无需求或不支持，关闭时使用 `Invalid`，不要使用 `won't do`。
5. Bug 不要关联到 Story；如知道研发任务，可 related to 到对应 Task。
6. 需求/交互/视觉链接要贴最细级子目录，Epic、一级 story、二级 story 要齐全，目标是评审后即可流转。

## 语音需求指南学到的规则

1. 语音链路按 `ASR -> NLU -> DS -> 车端执行` 判断：ASR 看识别文本，NLU 看 domain/intents/slots/tagging，DS 看功能点和参数下发，车端看执行。
2. 功能点是语音需求的真正管理落点；判断语音 bug 时不能只看 Jira 描述，必须落到 `meta_id`、标准功能点和深蓝项目功能点。
3. 项目功能点原则上尽量继承标准功能，只有标准功能确实不能满足时才新建；如果只是项目参数取值范围变化，不应新建功能点。
4. 项目产品员通常只能修改项目功能点的执行策略，不能改功能点元数据和示例指令；元数据变化需要算法配置员创建/拆分功能点。
5. 执行策略要指导工程师匹配已有 HMI 功能调用，不写具体实现逻辑；执行动作用 1-2 句话，复杂细节写说明。
6. 前置条件要按顺序写：先判断目标值是否已匹配，再判断挡位、车速、最大/最小范围、不支持、前提不满足等阻塞条件，最后写正常执行动作。
7. 语音前置条件不能照抄 GUI PRD 的具体细节，只表达需要应用侧判断的条件类别，降低维护成本。
8. TTS 尽量选已有条目；新增 TTS 需要谨慎，并由对应负责人和陈可评估。
9. UI 变化可能引起语音变化，车型产品经理要主动识别并走语音需求变更流程。
10. 动态技能申请必须包含 Jira 链接、项目车型、拦截句式、执行功能点链接和回复 TTS。

## AI 实战笔记学到的工作流

1. AI 不能代替产品决策；它负责检索、整理、预审、生成底稿，最终判断必须由产品侧口径闭环。
2. 对复杂问题要拆节点：资料检索、事实抽取、功能拆解、初步判断、人工/leader 复盘、规则沉淀，不要一口气生成完整结论。
3. 每次输出要有可追溯来源，避免凭模型记忆或标题判断。
4. AI 输出要有对错复盘和测试集意识；bug 表颜色只用于人工审核 Agent 准确性，不用于我自行分类。
5. 对文档/表格抽取任务，必须保留“待确认/未读到/不可访问”标记，不能补全不存在的信息。
6. 稳定有效的提示词、判断规则和反例要沉淀为本地 workflow，后续同类 bug 先查沉淀规则再判断。

## 语音功能点检查表范式

- 检查项目功能点的 `MetaId`、功能状态、来源状态、标准功能、更新时间。
- 分别检查执行策略/TTS、自定义 TTS、泛化/设置项范围、是否需要置草稿。
- 对“需要添加到说明的 query”和“有疑问的泛化、设置项范围”单独记录，方便找陈可或对应负责人处理。

## 后续执行规则

- 处理 bug 前：先看 Jira 全量信息，再查工作说明/Drive/语音平台/UE。
- 判断转需求：只有现有需求未覆盖但用户预期合理时转；实现缺陷转研发，测试预期错误或无需求则关闭 `Invalid`。
- 写表：短句写产品结论和责任方，不把培训文档里的长流程塞进单元格。
- 需要拆票：在 `预期处理方式` 或 `复盘后预期处理方式` 里直接写出拆票对象和关联关系。
- 语音 bug 写结论时必须明确是 ASR、NLU/标注、DS/功能点、项目执行策略、TTS、车端执行还是需求新增。

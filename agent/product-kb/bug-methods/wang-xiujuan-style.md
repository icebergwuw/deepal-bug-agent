# 王秀娟前 20 条 Bug 处理风格校准

来源：王秀娟工作说明表 `Sheet3` 第 2-21 行；逐条核对 Jira 字段、评论时间线、关联票、可读取的图片/PDF/xlsx、Drive 需求资料和当前 bug 表写法。

本文件用于校准产品 Agent 的判断方式，不替代当前 Jira、正式 UE/PRD、客户最终结论或 Alchemy 项目功能点。表中 MasterGo 链接在本轮没有可用连接能力，不视为已读取。

## 核心风格

王秀娟的优势是“结论先行、动作收口”：先把问题归类为非问题、接受现状、研发修复、转需求、重复问题或修改用例，再写责任方和关联票。她不会把每个 Jira 都默认当成研发缺陷。

最值得复用的模型是：

1. 先判断测试预期是否有需求、UE、配置或客户结论来源。
2. 再判断当前实现是符合定义、实现错误，还是合理能力缺失。
3. 最后只留下一个可执行动作：关闭、接受现状、转指定责任方、转需求或合并代表票。

## 对当前处理方式的改进

- C/J 列保留证据和链接，D/G/H 只保留最终动作，避免同一句结论在多个列重复。
- D 列统一写成“结论；责任方；动作”，不保留没有出口的问句和过多条件分支。
- `待确认`、`待会诊` 必须同时写明阻塞问题、责任人和下一步；没有明确阻塞项就先给当前结论。
- 建需求、需求已完成、需求最终决定维持现状要分开记录，不能把中间状态当最终状态。
- 关闭非问题时必须保留一条边界或依据；接受现状不等于研发已修复。
- 同根因问题优先保留代表票，其他票关联、关闭或转需求跟踪。
- 语音问题仍保留在线对话、`meta_id`、标准功能和深蓝项目功能点链路；不能为了追求短句而省略语音证据。

## 研发评论的使用边界

研发评论应提高权重，但提高的是“实现事实、根因和修复状态”的权重，不是直接替代产品口径。详细规则见 `rules/jira-comment-signals.md`。

可复用的最终表达：

- `当前行为符合生效 UE，按非问题关闭；责任方：测试修正用例。`
- `需求未定义但用户预期合理，关联代表需求票；原 bug 按需求跟踪关闭。`
- `已有能力但缺少配置、query 或项目继承，转对应语音/NLU/运营平台处理，不新增功能点。`
- `研发评论已给出实现根因和回归结果，但目标行为仍以生效 UE 及最新客户结论为准。`

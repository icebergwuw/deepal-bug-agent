# Bug Evidence Contract

当前版本与变更记录统一见 `agent/rules-version.md`。

这是 Bug 证据语义、来源优先级和结论门槛的唯一权威文件。可组合证据画像及其必查动作只在 `agent/config/evidence-requirements.json` 维护为机器可读配置；`AGENTS.md`、工作流、表格契约、Skill 和脚本只消费这两个入口，不复制业务规则。

## 证据分类

每个 Bug 都必须区分：

1. `正式产品定义`：当前生效的主 PRD、专项 PRD、交互文档、可读 UE、项目配置或功能点明确规定的目标行为与适用边界。
2. `当前实现事实`：Jira 描述、评论、日志、截图、视频、可复现结果和研发说明证明当前如何运行。
3. `规则空白`：正式资料未定义、资料不可读、入口失效、版本不明或多个正式来源互相冲突的部分。

研发所说“当前逻辑如此 / 可见优先 / 设计如此 / 历史如此 / 若调整需需求”只能证明实现、历史或调查方向；没有生效正式资料或客户最终结论时，不能单独作为关闭、非 Bug 或设计如此的依据。

### 机器可校验的来源角色

决策核验清单中的每条 `scope_checks` 必须有唯一 `source_id`，并且只承担一个角色：

- `formal_target`：直接定义本票目标行为的生效正式来源。Jira 测试预期、研发评论、Alchemy 当前输出、实现日志、“设计如此”和历史案例不得标成该角色。
- `implementation_actual`：证明当前实现、复现结果或实际平台输出的来源；不能反向定义产品目标。
- `context_only`：用于范围桥接、继承声明、冲突说明、异车型对照或检索线索；不能单独支撑确定性结论。

每条 `scope_checks` 还必须按 `agent/config/evidence-requirements.json` 登记 `source_type`。来源角色说明“这条资料在本票承担什么证明责任”，来源类型说明“它实际是什么资料”，两者不能混用：

- Jira、Jira 附件、Alchemy 当前输出、实现日志、测试结果、工作说明和历史资料不得标为 `formal_target`。
- Alchemy 标准/项目功能点可以证明语义、槽位或项目执行策略，但不能单独证明 UI、页面状态或产品交互目标。
- 确定性结论的预期行为卡必须至少引用一个产品正式定义类型：PRD、专项 PRD、交互、UE、生效配置或客户最终结论。
- `source_type` 的枚举、允许承担 `formal_target` 的类型和产品正式定义类型只在机器配置维护。

`match` 与角色共同决定来源是否有效：

- `formal_target + exact` 才能直接证明目标行为。
- 不同车型或项目的 `formal_target + partial` 只有在 `inheritance_chains` 中同时引用同项目的 `context_only + exact` 继承声明和被继承定义，并标记 `verified=true` 后才可使用。
- `implementation_actual + exact` 才能证明本票当前行为；`partial` 只能用于补充。
- `mismatch` 一律排除，不得被预期行为卡或结论引用；把它写成 `formal_target` 也不会提升证据等级。
- `gap` 必须声明 `material=true/false`。会改变目标行为、责任方或关闭判断的关键缺口标为 `material=true`，同时写 `next_action`；存在关键缺口时只能降级为 `待复核 / 待确认 / 待会诊`。不影响本次结论的资料缺口可标为 `material=false`，但必须说明理由。

## 来源优先级

1. 当前 Jira 的字段、描述、附件和完整评论时间线。
2. 生效主 PRD及与本问题直接相关的专项 PRD、交互文档、UE、配置和项目资料。
3. Alchemy 当前在线结果、标准功能和深蓝项目继承功能点。
4. 当前工作说明及其原始资料入口。
5. `agent/product-kb/` 中当前为 `verified` 且适用范围匹配的条目。
6. 历史案例、会议、培训、快照和 archive，仅作检索线索与历史证据。

不能用低优先级来源覆盖当前 Jira或生效正式定义。文件修改时间不是资料有效性的证明。

## 必查深度

- 每份正式资料必须落到会改变判断的具体章节、条款、图层、配置项或功能点，记录文档名称、版本、适用范围、精确证据位置和原始入口。
- `source_location` 是必填的可复查定位：PDF/PRD/交互写“页码 + 章节/区域/条款”，表格写“Sheet + 行号或序号 + Key/系统需求编号”，UE 写“页面/画板 + 图层”，Jira 写“描述/评论作者与时间/附件名 + 时间码”，Alchemy 写“功能点名称 + meta_id”。只写文档名、只写链接或只写检索关键词不算完成定位。
- AI 大模型、地图出行、跨域交互等存在专项资料的模块，除主 PRD外还必须按 query、功能名、`meta_id`、页面和交互阶段检索直接相关的专项资料。
- 判断测试预期前，先核对用户场景、车型、版本、当前行为和目标行为是否在同一适用范围。
- 找不到或读不到资料时，记录检索日期、已查入口和具体限制；“未读到”不能改写成“没有定义”。
- 检索命中 UE、PRD、交互、配置或资料索引等强候选时，必须打开正文并继续读取其中关联的原始入口；每个候选都标明 `read / excluded / unavailable` 及理由。候选未审完时不得写 `not_found`。
- “已读正式资料但未找到本票目标条款”必须登记该资料为 `read` 来源，并另记 `gap`；不得把“资料内缺少定义”伪装成“未找到资料”。

## 证据画像与必查资料

每个新建、普通复查和复盘 Bug 都使用 manifest `schema_version=5`，并在读取资料前完成 `evidence_profile_assessment`。必须对配置中的每个画像分别写 `applicable=true/false` 和理由，再把适用画像写入 `evidence_profiles`；不能只登记命中的画像而静默跳过其他画像。

画像可组合，不是单选分类：

- `general`：不属于其他专项画像的通用产品定义问题。
- `voice`：语音、ASR、NLU、VUI、Alchemy 或语音执行链。
- `map_navigation`：地图搜索、POI、路线规划、导航执行或路线偏好。
- `visible_interaction`：可见即可说、页面、控件、卡片、弹窗、节点或前置状态切换。

每个画像的必查动作只从 `agent/config/evidence-requirements.json` 展开到 `required_evidence_checks`。每条必查动作必须记录：

1. `check_id` 和 `status=read / not_found / unavailable / not_applicable`。
2. `searched_at`、实际检索入口 `search_location` 和非空 `queries`；每条 query 必须按机器配置登记 `{kind, text}`，覆盖该必查动作要求的检索维度。只写 Jira key、标题截断、“查过 Drive”或无类型字符串不算完成。
3. `read` 时引用已登记且类型匹配的 `source_ids`。
4. `not_found / unavailable` 时记录 `reason`、`material` 和关键缺口的 `next_action`。
5. 只有机器配置明确允许时才能使用 `not_applicable`，并写核验理由；不能用它跳过应查资料。
6. 对机器配置要求候选审计的 Drive 检索，`read / not_found` 都必须保存连接器返回的 `search_receipts`，并在必查动作中用 `search_receipt_ids` 绑定；回执记录查询、时间和每个结果的 id、标题、入口与 MIME 类型。
7. `candidate_audit` 的数量和候选 id 必须与绑定回执逐项一致；每个结果都标记 `read / excluded / unavailable` 并说明去留。不能人工填写 `results_count=0` 隐藏回执中的命中项；存在已读候选时不得标为 `not_found`。
8. 每个候选必须用 `references` 数组声明正文中出现的文档全名或原始资料入口；没有引用也显式写空数组。命中功能清单、配置索引、资料目录或其他二级入口时，必须按引用的完整文档名继续检索，并在 `search_completion.referenced_sources` 绑定 `exact_document_name` 回执。引用链未闭环时不得写 `not_found` 或进入写表。
9. 标题含版本号的候选必须登记 `version_family`，在 `search_completion.version_families` 保存同系列枚举回执、选中的已读候选、选择理由和 `newer_version_checked=true`。只打开搜索排序靠前的旧版本，不等于找到生效版本。
10. `search_completion.completed` 必须为 `true`；`referenced_sources` 和 `version_families` 即使没有项目也必须显式为空数组。宽泛关键词检索、精确文档名追查和版本族枚举可以分属不同回执，必查动作绑定的全部回执合并覆盖其声明查询。
11. manifest 必须用 `run_context` 绑定同一批次的 `run_id`、操作者、目标负责人、页签和 1-based 行号；单票 manifest 不得脱离本次运行上下文复用。

完整流程即使最终状态为待复核、待确认或待会诊，也必须完成检索动作或记录不可用限制。缺少必查动作本身不能通过门禁；已执行检索但关键资料未找到时，记录为 material gap 并降级。UE 只由 `visible_interaction` 等相关画像要求，纯后端或纯语义问题不一律强制读取 UE。

## 客户提报 Bug 与测试用例门槛

- Jira 标题或描述开头带一串非 Jira Key 的客户问题编号时，定义为客户提报 Bug；在核验卡中记录该客户问题编号和 Jira 原始入口。
- 客户提报 Bug 必须检查客户测试用例是否完整。完整用例至少包含车型/项目、软件版本、前置状态、完整操作步骤、输入或触发动作、预期结果、实际结果，以及能支持复现的截图、视频或日志入口。
- Jira 中的一句话现象、单张结果截图、研发实现说明或单独的客户预期，不能替代完整客户测试用例。
- 客户测试用例缺失或不完整时，生效正式定义和研发日志只能用于说明当前定义与实现，不能单独支撑 `可关闭 / 非 Bug / 设计如此`；状态保持 `待确认`，处理动作写为由当前产品负责人向客户收集测试用例后复核。
- 收到客户测试用例后，逐项核对用例前提与正式定义的车型、版本、触发方式和目标行为；若客户预期与现行定义冲突，拆分执行缺陷与需求变更，不把两者合并关闭。

## 决策核验卡与关联票

在写入任何新建、普通复查或复盘结论前，必须完成决策核验卡并用 `agent/scripts/validate_bug_evidence_gate.py` 校验；确定性结论额外受正式目标、实现事实和 material gap 门槛约束。核验卡写入本票操作日志，字段不可省略：

1. `备注因果链`：按完整评论时间线写出现象、责任模块诊断、根因或已知限制；研发详细日志、复现、版本和回归结果可作为高强度的**实现事实**，但不单独定义用户目标。
2. `客户问题识别`：写明是否存在标题/描述前置的客户问题编号；若存在，记录编号、客户测试用例是否已检查及 `complete / incomplete / missing` 状态。
3. `关联票`：列出已读取的直接关联 Jira、关系和各票对本单结论的影响；没有关联票也必须写明“已核验无直接关联票”。
4. `证据画像与必查资料`：逐项写画像选择/排除理由、必查动作状态、检索日期、入口、关键词、已读来源或不可用限制。
5. `资料适用范围`：每个改变结论的来源都要写唯一 `source_id`、`source_type`、`source_location`、来源角色、项目/车型、版本、触发方式、页面或交互阶段、目标行为，并标为 `exact`、`partial`、`mismatch` 或 `gap`；存在项目继承时另写可核验继承链。找不到或读不到时，`source_location` 写已查入口及具体限制，不得留空。
6. `冲突处理`：测试预期、关联票、评论和正式资料不一致时，逐项写出冲突及取舍理由；不能只选对某一方有利的证据。
7. `唯一结论`：写状态、包含“结论 / 依据 / 处理”的 `decision_text` 和唯一责任方。

批量日志必须使用 `## <Jira Key> 决策核验卡` 分段保存每票七项；一个通用核验卡不能覆盖多个 Jira。

### 关联票必读条件

- Jira 链接、评论、附件或日志表明同一根因、同一日志、重复提交、父子/关联关系，或存在会改变测试预期的相关票时，必须逐票完整读取后才能形成确定性结论。
- “共用日志 / 同一根因”只说明排查分组，不自动证明产品目标相同，也不自动等于重复票或非问题。
- 关联票的目标行为冲突时，除非上游结论已明确合并并覆盖各场景，否则保持 `待会诊`，明确冲突责任方和下一步；不得跳过冲突直接关闭或转研发。

### 资料范围与冲突取舍

- 同场景的项目/车型专项定义优先于不同项目、不同车型或不同触发方式的通用资料；后者最多补充，不能覆盖专项定义。
- 例如“系统设置关闭授权”与“运行时权限弹窗点击拒绝”是不同触发方式；没有直接来源连接两者时必须标为 `mismatch`，不能相互推导。
- 实现事实优先用可复现日志、视频、截图、回归结果和责任模块的详细分析；产品目标优先用同范围的生效项目定义、客户最终结论和已确认需求。两条线均要成立，才能形成确定性产品判断。
- 核验卡缺字段、关联票未读、范围不明或冲突未处理时，不生成确定性 `decision_text`，改为 `待复核 / 待确认 / 待会诊` 并记录缺口、责任方和下一步。

### 预期行为卡

形成确定性结论前必须填写 `expected_behavior`，逐项写清：

1. `trigger`：用户原话或操作。
2. `target_state`：应进入的功能状态。
3. `intent_function_signal`：应下发的意图、功能点、接口或信号；不适用时写明原因。
4. `ui_tts_vehicle_behavior`：UI、TTS 和车端应有的表现；不适用项写明原因。
5. `boundary`：车型、版本、前置状态和退出/异常边界。
6. `source_ids`：证明上述目标的有效 `formal_target`。

`decision.implementation_source_ids` 同时必须引用至少一条有效 `implementation_actual`。目标来源和实现来源必须分别成立，不能用同一条 Jira 测试预期同时替代两者。

## 语音 / NLU / VUI

1. `voice_evidence.applicable` 必须显式标记；语音、NLU、VUI 和语音执行问题标为 `true`。
2. 语音问题必须选择 `voice` 证据画像，并完成该画像在机器配置中定义的全部必查动作。
3. 在 Alchemy 在线对话输入 Jira 用户原话，记录原话、当前结果和 `meta_id`，并读取 `classification`、`operations`、槽位和返回结果。
4. 用 `meta_id` 打开标准功能详情，记录功能名和本票匹配判断。
5. 继续读取深蓝项目继承功能点，核对设置项、范围、泛化、执行策略、TTS 和状态；确认没有项目功能点时标为 `not_applicable` 并写明核验依据，不能因未读取而标记不适用。
6. 同时核对生效主 PRD及直接相关专项 PRD/交互文档；Alchemy 只证明语义和配置，不能单独证明产品交互目标。
7. 结论必须明确落到 ASR、NLU/标注、DS/功能点、项目执行策略、TTS、车端执行或新增需求。

语音证据只有同时具备 Jira 用户原话、Alchemy 当前结果、`meta_id`、已读标准功能点和已读项目功能点（或已核实 `not_applicable`）时，`availability` 才能标为 `complete`。平台不可访问、未返回 `meta_id`、功能标题不明或项目功能点未读时，标为 `partial / unavailable`，写明 `unavailable_reason` 和 `next_action`，状态只能为 `待复核 / 待确认 / 待会诊`，不得定责为 `可转语音 / 转语音`。

项目参数、范围、执行策略或 TTS 差异优先落到项目继承功能点；标准元数据、slot、intent、tagging 或拆分问题落到标准功能/NLU责任边界。具体责任映射从 `agent/product-kb/org/component-owner-map.md` 读取，不在本契约写死人员。

### 可见交互优先级

- 用户已处于当前页面、弹窗、卡片或其他前台交互上下文时，命中该上下文最上层可见节点的指令，优先于脱离当前页面的通用语义、后台上下文或其他不可见目标；不得用通用语义结果覆盖可见节点目标。
- “可见优先”只确定目标选择顺序，不等于任意可见节点都自动通过。若同一前台上下文存在多个可见节点命中同一原话，必须继续核验节点层级、互斥关系、序号范围和正式优先级/消歧定义；缺少定义时保持 `待复核 / 待确认 / 待会诊`。
- 已建立的特定任务上下文与可见节点冲突时，按当前正式产品定义判断；若没有更具体的生效定义，默认先处理当前最上层可见交互，并把上下文仲裁规则记录为待补齐的产品规则。
- 预期行为卡必须分别记录可见节点、当前任务上下文及二者的优先级关系；实现结果若违反上述顺序，按可见交互执行链的配置、仲裁或实现责任继续定位，不直接归因于通用 NLU。

## MasterGo UE

1. 优先从当前工作说明或 Drive 资料取得 MasterGo 短链或 `fileId + layerId`。
2. 只有 `page_id` 不能证明目标图层已读；MCP 返回空结构、文件在草稿箱、账号无团队项目权限或链接信息不足时，记录“未读到 UE”并补要图层链接或短链。
3. `.mastergo/` 本地缓存不是正式资料。
4. token 只通过安全运行时配置注入，不写入表格、日志、知识库、项目文件或回复。

## 结论门槛

- `可关闭 / 非 Bug / 设计如此 / Invalid / 可转研发 / 可转语音 / 转语音 / 转需求 / 转需求评估 / 待回归` 均为确定性状态；必须完成全部适用画像的必查动作，同时具备有效产品正式定义 `formal_target`、有效 `implementation_actual`、完整预期行为卡、无关键 `material gap`，并在结论中显式引用实现来源。
- `可关闭 / 非 Bug / 设计如此 / Invalid`：正式定义必须覆盖明确适用边界或存在客户最终结论。
- `可转研发 / 可转语音 / 转语音`：必须写清当前行为、目标行为、缺陷位置和责任边界；语音类还必须通过完整 Alchemy 证据链。
- `转需求 / 转需求评估`：必须用有效正式定义证明当前能力或范围未覆盖目标行为，并按不同系统责任边界拆票。
- 机器门禁根据证据完整性限制状态类别：命中客户用例缺失时固定降为 `待确认`；缺正式目标、缺实现证据、关键缺口或语音链不完整时，只允许 `待复核 / 待确认 / 待会诊`。具体选择哪一个降级状态仍由缺口类型决定，不能先写确定性 G 状态再补理由。
- 证据不足但仍可能改变判断时，保持 `待复核 / 待确认 / 待会诊`，在唯一风险中写明缺口、责任方和下一步。
